## 面试官指引

- 校招重基础和学习能力，不要求大规模生产经验，但会看候选人对自己项目里用到的技术是否真正理解。
- 八股题的覆盖面：Java 集合与并发、JVM 内存与 GC、MySQL 索引与事务、Redis 数据结构与缓存问题、TCP 与 HTTP。一场里每个方向最多一道，避免扎堆。
- 优先从候选人简历里出现过的技术出八股题，例如简历写了 Redis，就问 Redis 而不是 MongoDB。
- 场景题选和简历项目相近的业务，例如做过电商就问超卖、订单超时，做过社交就问 feed 流、点赞计数。
- 算法题只在题目数量 ≥ 5 时出一道。优先选带预置测试用例的题（本题包里写了用例的，或系统预置算法题），让候选人在编辑器里写代码，提交后自动判题；没有用例的算法题仍口述思路和复杂度。

## 评分要点

- 准确性：Java 版本差异要说对（例如 HashMap 1.7 头插 / 1.8 尾插加红黑树、ConcurrentHashMap 1.7 分段锁 / 1.8 CAS + synchronized），把旧版本当现状扣准确性。
- 深度：能讲到“为什么这样设计”和“代价是什么”才给 4 分以上，只背出名词最多 3 分。
- 实战关联：校招生没有生产数据不扣分，但能结合自己项目说明“在哪里用、遇到过什么问题”的加分；八股题不要求实战数据时，实战关联按“是否举出了恰当的使用场景”来评。
- 表达：先给结论再展开、能按条理分点的给 4 分以上；想到哪说到哪、反复改口的最多 3 分。

## 题目

### [八股] HashMap
HashMap 的底层结构是什么？put 一个元素的过程是怎样的，什么时候扩容？
- JDK 8 为数组 + 链表 + 红黑树，链表长度达到 8 且数组长度 ≥ 64 时转红黑树（数组不足 64 时先扩容）
- put：计算 hash（高 16 位异或低 16 位）→ 定位桶 → 空桶直接放，否则遍历链表或树，key 相同则覆盖
- 元素个数超过 容量 × 负载因子（默认 0.75）时扩容为 2 倍
- 扩容时元素要么在原位置，要么在原位置 + 旧容量，不需要重新算 hash
- 线程不安全：JDK 7 并发扩容可能形成环形链表，JDK 8 仍可能丢数据

### [八股] ConcurrentHashMap
ConcurrentHashMap 是怎么保证线程安全的？JDK 7 和 JDK 8 的实现有什么区别？
- JDK 7：Segment 分段锁，每个 Segment 是一个 ReentrantLock，并发度等于 Segment 数
- JDK 8：取消分段，空桶用 CAS 写入，非空桶对头节点加 synchronized
- 读操作不加锁，依靠 volatile 保证可见性
- 支持多线程协助扩容（transfer），size 用类似 LongAdder 的分段计数

### [八股] 线程池
讲讲线程池的核心参数，以及提交一个任务后的执行流程。
- 核心线程数、最大线程数、存活时间、任务队列、线程工厂、拒绝策略
- 流程：线程数 < 核心数则新建线程 → 否则入队 → 队列满且线程数 < 最大数则新建非核心线程 → 否则执行拒绝策略
- 四种拒绝策略：AbortPolicy、CallerRunsPolicy、DiscardPolicy、DiscardOldestPolicy
- 不建议用 Executors 创建：无界队列或无上限线程数可能导致 OOM

### [八股] JVM 垃圾回收
JVM 怎么判断一个对象可以被回收？常见的垃圾回收算法有哪些？
- 可达性分析：从 GC Roots（栈中引用、静态变量、常量、JNI 引用等）出发不可达的对象可回收；引用计数无法处理循环引用
- 标记-清除（有碎片）、标记-复制（浪费空间，适合新生代）、标记-整理（适合老年代）
- 分代收集：新生代 Eden + 两个 Survivor，Minor GC 后存活对象年龄增长，达到阈值晋升老年代
- 能说出一种具体收集器（如 G1 按 Region 回收、可设停顿目标）加分

### [八股] MySQL 事务隔离
MySQL 的四种隔离级别分别解决了什么问题？InnoDB 默认的可重复读是怎么实现的？
- 读未提交、读已提交、可重复读、串行化；分别对应脏读、不可重复读、幻读问题
- InnoDB 默认可重复读，通过 MVCC 实现快照读：undo log 版本链 + ReadView
- 读已提交每次查询生成新 ReadView，可重复读在事务第一次查询时生成并复用
- 当前读（select ... for update、update）通过临键锁（记录锁 + 间隙锁）防止幻读

### [八股] MySQL 索引
MySQL InnoDB 为什么用 B+ 树做索引？什么情况下索引会失效？
- 非叶子节点只存键，单页能放更多键，树高通常 3 层，磁盘 IO 少
- 叶子节点有序且用链表相连，适合范围查询
- 联合索引遵循最左前缀，范围查询后的列用不上索引
- 失效场景：对索引列用函数或计算、隐式类型转换、以 % 开头的 LIKE、OR 连接无索引列

### [八股] Redis 缓存问题
缓存穿透、缓存击穿、缓存雪崩分别是什么？各自怎么解决？
- 穿透：查询不存在的数据，请求直达数据库；用缓存空值或布隆过滤器
- 击穿：热点 key 过期瞬间大量请求打到数据库；用互斥锁重建或逻辑过期
- 雪崩：大量 key 同时过期或 Redis 宕机；过期时间加随机值、多级缓存、限流降级、Redis 高可用
- 能说明各方案的代价（如空值占内存、布隆过滤器误判、互斥锁降低吞吐）加分

### [八股] TCP 连接管理
TCP 为什么是三次握手、四次挥手？TIME_WAIT 状态的作用是什么？
- 三次握手确认双方的发送和接收能力都正常，并同步初始序列号；两次握手无法防止历史连接请求
- 四次挥手是因为 TCP 全双工，一方关闭发送后另一方可能还有数据要发，ACK 和 FIN 分开发送
- TIME_WAIT 持续 2MSL：保证最后一个 ACK 能重传、让旧连接的报文在网络中消失
- 大量 TIME_WAIT 出现在主动关闭方，可以用连接池或长连接缓解

### [场景题] 秒杀防超卖
设计一个秒杀下单流程，怎么保证库存不超卖，同时扛住瞬时高并发？
- 数据库层：update 库存 set stock = stock - 1 where id = ? and stock > 0，利用行锁保证不超卖
- 前置拦截：Redis 预扣库存（Lua 脚本保证原子性），库存不足直接返回
- 削峰：下单请求进消息队列异步创建订单，前端轮询结果
- 防重复：用户维度去重（Redis SETNX 或唯一索引），限流和验证码挡住脚本
- 一致性：Redis 与数据库库存不一致时的对账与补偿

### [场景题] 订单超时取消
下单后 30 分钟未支付要自动取消订单，你会怎么实现？各方案有什么优缺点？
- 定时任务扫表：实现简单，但有延迟、扫表压力大
- 延迟消息：RocketMQ 延迟消息、RabbitMQ 死信队列或延迟插件，精度高、解耦
- Redis 有序集合按过期时间排序轮询，或 Redis key 过期通知（不可靠）
- 取消时要和支付回调做并发控制（状态机 + 乐观锁），保证幂等

### [算法] LRU 缓存
实现一个 LRU 缓存，要求 get 和 put 的时间复杂度都是 O(1)，说说思路。
- 哈希表 + 双向链表：哈希表 O(1) 定位节点，双向链表 O(1) 移动和删除
- get 命中后把节点移到链表头；put 已存在则更新并移到头，不存在则插入头部
- 超出容量时删除链表尾节点，并从哈希表中移除
- Java 中可以用 LinkedHashMap（accessOrder = true，重写 removeEldestEntry）

### [算法] 爬楼梯
每次可以爬 1 或 2 级台阶。给定正整数 n（1 ≤ n ≤ 45），求爬到第 n 级有多少种不同的方法。从标准输入读入一行一个整数 n，向标准输出打印方法数。例如 n 为 3 时输出 3。
- 递推：f(n) = f(n-1) + f(n-2)，f(1) = 1，f(2) = 2
- n 到 45 时结果仍在 32 位有符号整数范围内
- 时间 O(n)，空间 O(1)

```cases
3
---
3
===
name: 一阶
1
---
1
===
name: 两阶
2
---
2
===
name: 五阶
5
---
8
```
